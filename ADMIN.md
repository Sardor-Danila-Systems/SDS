# SDS Admin — как запустить и как пользоваться

Внутренний инструмент SDS: CRM для продаж + CMS для контента публичного сайта.
Живёт на `/admin`, в поиск не индексируется.

---

## 1. Что нужно сделать прямо сейчас

Два пункта, без которых система работает не полностью.

### 1.1. Переключить Vercel Blob на публичный доступ ⚠️

**Это блокер для продакшена.** Сейчас стор создан с приватным доступом, и любая
запись отклоняется:

```
Vercel Blob: Cannot use public access on a private store.
```

Из стора читаются и данные, и картинки проектов — их URL должны открываться из
браузера, поэтому нужен именно публичный стор.

Как починить:

1. Vercel → проект → **Storage** → ваш Blob store → **Settings**.
2. Переключить access на **Public**. Если переключателя нет — создайте новый
   публичный стор и подключите его к проекту.
3. Скопировать новый `BLOB_READ_WRITE_TOKEN` в переменные окружения.
4. Передеплоить.

Пока это не сделано, CRM пишет в локальный файл `.data/crm.json` (в гит не
попадает). На дашборде висит строка с причиной. Локально всё работает — просто
данные не покидают вашу машину.

Проверить, что починилось: зайдите на `/admin` — если строки про локальный файл
нет, значит пишется в Blob.

### 1.2. Убрать `.env` из гита 🔐

`.env` закоммичен вместе с токеном Blob, паролем админа и секретом сессий:

```bash
git rm --cached .env
echo ".env" >> .gitignore
git commit -m "chore: stop tracking .env"
```

После этого **перевыпустите** `BLOB_READ_WRITE_TOKEN` и смените
`ADMIN_PASSWORD` / `ADMIN_SESSION_SECRET` — старые значения остались в истории
репозитория.

## 2. Переменные окружения

| Переменная | Зачем | Обязательна |
|---|---|---|
| `ADMIN_LOGIN` | Логин админа «на всякий случай» — им нельзя заблокировать себе вход | да |
| `ADMIN_PASSWORD` | Пароль к нему | да |
| `ADMIN_SESSION_SECRET` | Подпись JWT сессии. Длинная случайная строка | да |
| `BLOB_READ_WRITE_TOKEN` | Хранилище данных и загрузка картинок | для прода |
| `CRM_STORE` | `file` или `blob` — принудительно выбрать хранилище | нет |

Сгенерировать секрет:

```bash
node -e "console.log(crypto.randomUUID()+crypto.randomUUID())"
```

## 3. Запуск

```bash
npm install
npm run dev      # http://localhost:3000
```

Проверки перед деплоем:

```bash
npm run typecheck
npm run lint
npm run build
```

## 4. Вход и пользователи

Зайти: `/admin` → редирект на `/admin/login`, логин и пароль из `.env`.

**Роли и что они могут:**

| | ADMIN | SALES | DEVELOPER |
|---|---|---|---|
| Смотреть CRM | ✓ | ✓ | ✓ |
| Prospects, лиды, клиенты | ✓ | ✓ | — |
| Свои задачи, встречи | ✓ | ✓ | ✓ |
| Задачи всей команды, назначать задачи | ✓ | — | — |
| Страница «Команда», аккаунты | ✓ | — | — |
| Видеть суммы | ✓ | ✓ | — |
| Платежи и расходы (запись) | ✓ | — | — |
| Страница «Финансы» | ✓ | — | — |
| Удалять записи | ✓ | — | — |
| Контент сайта | ✓ | — | — |

Права проверяются **на сервере, внутри каждой операции** — спрятать кнопку
недостаточно, и подделанный запрос будет отклонён так же.

**Добавить сотрудника.** `Команда` → форма «Новый аккаунт»: имя, логин, пароль
(от 8 символов) и роль. Сотрудник из отдела продаж видит только свои задачи,
лиды, воронку, клиентов и проекты; финансов компании, портфолио и страницы
«Команда» у него нет — это проверяется на сервере. Отключить аккаунт можно там
же, доступ пропадает сразу, не после истечения сессии.

**Профиль и пароль.** Имя сотрудника в левом меню ведёт в `Профиль`: там смена
пароля (текущий, новый от 8 символов, повтор). На входе и во всех полях паролей
есть «глазик» для показа вводимого. Если сотрудник забыл пароль, админ на
«Команде» → «Задать новый пароль». Пароли хранятся только в виде хеша, увидеть
текущий пароль нельзя — только задать новый. Пароль самого админа берётся из
`ADMIN_PASSWORD` на сервере и меняется там.

**Аналитика** (только админ). Раздел `Аналитика` собран из четырёх карточек:
«Получено» за 30 дней (накопленным итогом, с изменением к предыдущим 30 дням);
активность команды по часам суток (продажи и разработка, три недели, по журналу
действий CRM); «Получено по проектам» за неделю / месяц / год с таблицей топ-клиентов;
сезонность поступлений по месяцам за этот и прошлый год. Графики показывают
подсказки при наведении. Суммы разных валют не складываются: валюта (UZS / USD)
выбирается справа вверху. Плитки статистики на «Сегодня», «Контроле», «Финансах» и
в статистике созвонов оформлены в том же стиле.

**Созвоны** (только админ). Раздел `Созвоны` — журнал дэйликов. В списке: ближайшие
и прошедшие созвоны с датой, темой, организатором и тем, сколько пришло;
закреплённые итоги сверху; «Не было на последнем созвоне» с причинами.

В карточке созвона: таблица посещаемости, где статус меняется прямо в строке
(Присутствовал / Опоздал / Отсутствовал / Предупредил / Уважительная причина /
Не отмечен). Для отсутствия и опоздания появляется причина — готовый вариант
(болезнь, учёба/работа, технические проблемы, предупредил заранее, личная
причина, другое) и/или свой текст; причина необязательна. Кнопка «Все
присутствовали» отмечает тех, кто ещё не отмечен. Можно добавить гостя, которого
нет в системе. Ниже — тема, ссылка, повестка (есть шаблон «вчера / сегодня /
блокеры»), заметки по ходу, итоги (их можно закрепить) и отметка «проведён».
Созвон можно перенести или отменить с причиной; каждое изменение записывается
в историю (кто, когда, какой статус был).

Задачи после созвона создаются в карточке и попадают в трекер; на следующем
созвоне блок «Не закрыто с прошлых созвонов» показывает всё, что осталось
открытым, со сменой статуса прямо там. Расписание (дни недели, время, тема,
ссылка, повестка) включается в правой колонке списка: созвоны создаются сами на
неделю вперёд, а новые сотрудники добавляются в участники. Статистика: процент
посещаемости по людям и команды, пропуски, опоздания, динамика по месяцам; у
каждого человека есть своя страница с историей.

Статистика считает созвоны, где отмечен хоть кто-то и которые не отменены; человек
учитывается на созвоне, только если он на нём отмечен. Время созвона хранится как
дата и часы по Ташкенту, без пересчёта часовых поясов.

**Контроль** (только админ) — «личная Jira» руководителя. Переключатель отдела
(все / продажи / разработка) и периода (7 / 30 дней). Показаны: сколько задач
выполнено, сколько открыто, на проверке и просрочено, доля сданных в срок и
среднее время выполнения; график «Выполнено по дням» по отделам; рейтинг «Кто
сколько сделал» (сделано, открыто, просрочено, в срок). Ниже — доска по
сотрудникам: у каждого человека своя дорожка со статусами. Перетащите карточку
в другую колонку — сменится статус, на дорожку другого человека — задача
перейдёт к нему. Внизу лента «Недавно выполнено». Отдел определяется ролью
исполнителя; задачи самого админа видны только в «Все».

**Трекер задач** (`Трекер`, как в Jira). Доска из четырёх колонок: К выполнению →
В работе → На проверке → Готово; карточки перетаскиваются мышью. У каждой
задачи сквозной номер (SDS-1, SDS-2…), исполнитель, приоритет, срок и
необязательная привязка к проекту клиента. В карточке задачи — описание,
комментарии и история изменений.

Админ видит задачи и разработчиков, и отдела продаж: фильтры по отделу
(отдел = роль исполнителя), исполнителю, приоритету и поиск, переключатель
«Доска / Список». Ставит задачи кнопкой «Новая задача», выбрав исполнителя, и
может переназначать их в карточке. Разработчик и продажник видят и двигают
только свои задачи и могут их комментировать. Просроченные задачи попадают в
уведомления исполнителя и админа.

## 5. Как устроена система

```
/admin                    сегодня: что горит
/admin/crm/leads          лиды + карточка с историей
/admin/crm/pipeline       воронка (drag & drop)
/admin/crm/tasks          задачи
/admin/crm/meetings       встречи
/admin/crm/prospects      «Кому написать» — компании до первого контакта
/admin/crm/clients        клиенты
/admin/crm/projects       проекты клиентов + деньги
/admin/crm/finance        финансы: получено, расходы, баланс, кто должен
/admin/content            портфолио на публичном сайте (CMS)
/admin/analytics          аналитика (только админ): поступления, активность, сезонность
/admin/control            контроль работы (только админ): отделы, статистика, доска по сотрудникам
/admin/tracker            трекер задач: доска и список, карточка задачи
/admin/team               команда: кто чем занят, лента событий, аккаунты
/admin/standups           созвоны (дэйлики): посещаемость, итоги, задачи, статистика
```

**Важно:** «Проекты клиентов» и «Проекты в портфолио» — разные вещи и намеренно
не смешаны. Первое — коммерческая работа, которую вы делаете за деньги. Второе —
кейс на сайте. Проект можно связать с портфолио, если решите опубликовать.

## 5.1. Оформление и тема

Админка имеет светлую и тёмную тему: переключатель внизу меню (на телефоне —
в верхней панели). При первом заходе тема берётся из системы, дальше
запоминается в браузере. Стили админки лежат в `app/admin/admin.css` и
действуют только внутри `/admin`, публичный сайт они не затрагивают.

Админ видит всю работу отдела продаж: в `Лиды` есть колонка «Ответственный» и
фильтр по сотруднику, в карточке лида — владелец, на «Сегодня» — блок по
команде, на «Команда» — лента действий.

## 6. Рабочий процесс

### Основной путь

```
Кому написать → Лид → Клиент → Проект → Платежи
```

**1. Нашли компанию.** `Кому написать` → форма справа: компания, контакт,
телефон, что можем сделать, примерный бюджет. Полей мало намеренно — остальное
потом.

**2. Ответили — переводим в лиды.** Кнопка `В лиды →`. Компания не удаляется:
она остаётся в списке со ссылкой на лид, повторно конвертировать нельзя.

Если контакт пришёл сам — сразу `Лиды` → `Новый лид`, минуя список.

**3. Ведём переговоры.** Карточка лида — главный экран:

- **Этап** меняется в один клик, каждая смена попадает в историю;
- **Следующее действие** — что и когда сделать. Если дата прошла, дата
  краснеет, лид попадает в уведомления и на дашборд;
- **История** — записывайте звонки и встречи. Смена этапа и платежи туда
  пишутся сами.

**4. Назвали цену.** Этап `КП` в карточке лида, сумма — в поле `Наша цена`.
Отдельного экрана коммерческих предложений больше нет: цена и этап живут там,
где живёт сделка. Факт отправки записывается в историю (`КП отправлено`).

**5. Выиграли.** В карточке лида — `Перевести в клиенты`. Лид не исчезает:
получает статус `WON` и ссылку на клиента.

**6. Начали работу.** `Проекты клиентов` → выбрать клиента. Описание, цена и
требования подтягиваются из лида — заново вводить не нужно.

**7. Получили деньги.** В карточке проекта — форма платежа. Остаток считается
сам, история платежей видна рядом.

**8. Общая картина.** `Финансы`: получено (сумма платежей), расходы, баланс и
сколько клиенты ещё должны — отдельно по каждой валюте, плюс разбивка по
месяцам и проектам. Расходы (зарплаты, сервисы, маркетинг, налоги, прочее)
вносит админ, можно привязать к проекту. Удаление — мягкое.

### Воронка

Шесть колонок: Новый → Связались → Встреча → КП → Сделка / Отказ. Лиды, заведённые
до сокращения этапов, показываются в ближайшей колонке (`Интерес` → `Связались`,
`Переговоры` → `КП`) — ни одна карточка не пропадает.

`Воронка` — перетаскивание карточек между колонками. Смена этапа пишется в
историю лида. На телефоне таскать неудобно — там меняйте этап кнопками в
карточке лида.

### Поиск и уведомления

В шапке. Поиск ищет по лидам, клиентам, компаниям из списка и проектам — по имени,
компании, почте, телефону, городу. Уведомления считаются из самих записей:
просроченные задачи, встречи сегодня, follow-up, у которых наступил срок.

## 7. Данные

Всё лежит одним JSON-документом: `data/crm.json` в Blob (прод) или
`.data/crm.json` (локально).

**Что гарантируется:**

- ничего не удаляется физически — soft delete;
- конверсии связывают, а не переносят: цепочка
  `prospect → lead → client → project` прослеживается в обе стороны;
- каждое изменение пишется в журнал: кто, что, когда;
- сохранения выполняются по очереди: два одновременных сохранения больше не
  перетирают друг друга (`mutateCrm` в `lib/crm/store.ts`).

**Почему это быстро.** Документ читается целиком, поэтому чтения удешевлены
в трёх местах: адрес файла в Blob вычисляется один раз на процесс, все запросы
одного экрана делят одно чтение (`cache` в `lib/crm/repo.ts`), а результат
переиспользуется несколько секунд между запросами. Успешная запись сразу
кладёт сохранённое в этот кэш, поэтому экран после сохранения показывает новые
данные, не ходя в Blob.

**Резервная копия** — просто скачайте JSON:

```bash
# локально
cp .data/crm.json ~/backup-$(date +%F).json
```

Для прода — скачать `data/crm.json` из Blob через дашборд Vercel.

**Когда перерастёте JSON.** Один документ переписывается целиком на каждое
изменение — это нормально для команды в несколько человек и десятков сделок в
месяц. Когда станет тесно, менять нужно **только** `lib/crm/store.ts`: всё
остальное ходит через `readCrm` / `writeCrm` и про хранилище не знает.

## 8. Что не сделано

Осознанно, чтобы не размазать качество:

- **PDF для КП.** Экран коммерческих предложений убран из меню (цена и этап
  живут в карточке лида), но модель `Proposal` и операции в `lib/crm/repo.ts`
  на месте — если понадобится документ с составом работ, экран возвращается
  вместе с отрисовкой PDF.
- **Экран управления пользователями** — пока через консоль (см. §4).
- **Календарь встреч** — сейчас список с разделением «ближайшие / прошедшие».
- **Аналитика:** конверсия по этапам, средний цикл сделки, отчёты по источникам.
- **Связь проекта клиента с кейсом в портфолио** — поле `portfolioSlug` в
  модели есть, интерфейса нет.
